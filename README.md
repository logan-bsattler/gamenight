# Game Night

A browsable shelf of the 143 board games in `bsatt33`'s BoardGameGeek
collection. Filter by players, time and complexity, or say what tonight feels
like and let it pick.

**Live:** <https://logan-bsattler.github.io/gamenight/> — GitHub Pages, served
straight off `main`. A push is a deploy; there is no build step.

Installable: it has a manifest and a service worker, so it can go on a phone's
home screen and the shell opens without a network (the cover art still needs
one).

## The shape of it

Everything the app does is in one file.

```
index.html          the whole app: CSS, markup, GAMES data, VIBES block, JS
  ├─ GAMES          one object per game, from BGG. Hand-maintained.
  └─ VIBES          eight 0-100 axes per game. GENERATED - see below.
sw.js               offline shell, network-first
manifest.json       + favicon.svg, icon-{192,512}.png, apple-touch-icon.png, og.png
tools/make_icons.py regenerates those images (needs Pillow)
vibes/              the vibe scorer: its own README, pipeline and data
REVIEW.md           a review of the app and what has been done about it
```

`index.html` is ~200KB and ~1250 lines, most of it the two data blocks: `GAMES`
runs from about line 419 and `VIBES` ends at 567, with all the application code
below that.

### The one generated region

```
/* VIBES:START -- generated by vibes/build_vibes.py, do not edit by hand */
```

Everything between the `VIBES:START` and `VIBES:END` markers is written by
`vibes/build_vibes.py`. Edit the scorer or `vibes/vibes-manual.json` and
rebuild; do not hand-edit the block. Nothing else in the file is generated —
presentation changes never need a rebuild.

## Running it locally

Opening `index.html` from disk mostly works, but `file://` and `data:` origins
break two things the app now uses: `history.replaceState` (so shared links and
presets go dead) and service workers. Serve it over http instead:

```bash
python -m http.server 8123
```

Then <http://localhost:8123>. `.claude/launch.json` has the same thing wired up
for Claude Code's preview pane.

## Refreshing the collection

Adding games is a manual pass, done with the `bgg` MCP server rather than a
script — see `a07ce26` for what a refresh commit looks like. Roughly:

1. Pull the collection for `bsatt33` and diff it against the ids in `GAMES`.
2. For each new game, add a record with the same fields as its neighbours.
   Cover art uses BGG's `previewthumb` or `itemrep` crop; keep the URL exactly
   as BGG gives it (the URLs are signed — see the note below).
3. Find a teach video where one exists. Some games have none; leave `video` off
   rather than linking something unhelpful.
4. Bump `UPDATED`, which the footer shows.
5. Refresh `vibes/bgg-cache.json` for the new ids and rerun the vibes pipeline,
   so the new games get scores.

There is a `refresh-bgg-collection` skill on this machine, but its description
names a *deal tracker* and an `OWNED` list, neither of which exists here. Check
what it actually targets before pointing it at this repo.

**Cover art is signed.** The `fit-in/246x300` in a BGG image URL cannot be
edited to get a bigger image: the signature in the path covers the transform,
and every altered size or preset returns 400. Larger art has to come from the
API's own `image` field on a fresh pull.

## The vibe scorer

Eight axes — cozy, silly, chatty, swingy, cutthroat, crunchy, tense, storied —
scored 0-100 for every game, used for the match score and the radar.
`vibes/README.md` is the real documentation, including where the model
knowingly departs from `vibe-scorer-spec.md`. The pipeline:

```bash
python vibes/vibe_scorer.py --report   # bgg-cache.json -> vibes-auto.json
python vibes/build_vibes.py            # + vibes-manual.json -> the VIBES block
python vibes/validate_vibes.py         # needs hand scores first
```

Validation is the open piece: `vibes/vibes-manual.json` is still `{}`, so
nothing has been checked against a human. Hand-score *before* reading
`vibes/vibes-auto.json`, or you are measuring your memory of the numbers.

## What it stores

In `localStorage`, per browser, never sent anywhere:

| Key | What |
|---|---|
| `gn-theme` | `light` / `dark`; absent means follow the OS |
| `gn-plays` | `{gameId: ["2026-09-04", ...]}` from the sheet's play log |
| `gn-presets` | `[{n: "Tuesday crowd", h: "vp=4&cozy=70"}]` |

Plays do not sync to BGG and do not follow you between devices. BGG's API is
read-only for plays, so posting one would mean holding your credentials; the
sheet says where the count lives and links out to the game's BGG page, which
carries BGG's own Log Play button.

No deep link straight to the log-play form: `/plays/edit/gameid/<id>` answers
"Invalid Item" and `geekplay.php?gameid=<id>&action=edit` answers "Play not
found" (it wants an existing play id). Both of those *look* fine logged out,
which is how the wrong one shipped once. BGG renders those routes client-side,
so curl returns the same shell for every candidate and cannot tell them apart
-- check any replacement while signed in, on the real site.

## Shareable links

Filter state lives in the URL hash, so any set of filters can be texted to
someone. Only non-defaults are written.

Four players, under an hour, something light with a teach video, leaning cosy
and not too crunchy — 43 games, best fit The Crew:

```
#p=4&t=60&w=light&s=name&vid=1&vp=4&cozy=70&crunchy=35
```

`q` search · `p` players · `two` 2-player-only · `t` max minutes · `w`
light/medium/heavy · `m` mechanic · `s` sort · `vid` has-teach-video · `award`
award-winner · `vp`/`vt` the vibe panel's players and time · and each axis under
its own name, 0-100.

Note `p` and `two` are separate filters that will contradict each other if you
set both, and `t` (the quick strip) and `vt` (the vibe panel) are separate time
budgets.

Unrecognised values are dropped rather than trusted; axis values clamp into
0-100. A preset is just one of these strings without the `q`, which is why
recalling a preset and opening a shared link are the same code path.
