# Game Night — Vibe Scorer Spec

Add six vibe axes to every owned game, scored automatically from BGG data, hand-correctable, and usable for a "what fits tonight" match score.

**Axes:** Cozy, Social, Playful, Compete, Intense, Thinky. Each 0–100.

---

## 1. Data pull

Source everything from the local `bgg-mcp` server. Two calls:

1. `collection` for the owned list — remember the expansion quirk (`exclude_subtype`), and that expansions come back labelled `boardgame`.
2. `get_games` with `stats=1`, batched, for the details.

Fields needed per game:

| Field | XML path | Use |
|---|---|---|
| `averageweight` | `statistics/ratings/averageweight` | Thinky base |
| subdomain ranks | `statistics/ratings/ranks/rank[@type="family"]` | vibe class signal |
| mechanics | `link[@type="boardgamemechanic"]` | most axes |
| categories | `link[@type="boardgamecategory"]` | most axes |
| playtime | `minplaytime` / `maxplaytime` | Intense, Playful |
| players | `minplayers` / `maxplayers` | Social |
| `suggested_numplayers` | `poll` | already used, keep |
| `language_dependence` | `poll` | "easy to jump in" filter |
| `minage` | `minage` | Playful |

Cache per the existing policy (~1 week on games). Rate limit already handled by the server.

`averageweight` comes back as `0` for unrated games — treat 0 as **null**, not as "very light". Fall back to the median weight of games sharing its primary category.

---

## 2. Scoring model

Each axis is a weighted sum of signals producing a raw score, then normalised. Signals are additive; a game can be both Social and Compete.

Subdomain ranks are a boolean per game (present or not). Presence matters more than the rank value — don't weight by position.

### Thinky
- Base: `(weight − 1) / 4 × 70`
- `+15` strategygames rank, `+10` abstracts rank
- `+5` each (cap 15): Worker Placement, Engine Building, Action Points, Tech Trees, Network and Route Building, Programmed Movement, Grid Coverage, Auction/Bidding
- `−25` partygames rank, `−30` childrensgames rank
- `−10` Roll / Spin and Move

### Cozy
- Base: `60 − (weight − 1) / 4 × 30`
- `+15` Cooperative Game, `+10` Solo / Solitaire Game
- `+8` each (cap 24): Tile Placement, Set Collection, Pattern Building, Open Drafting, Closed Drafting
- `+8` categories: Animals, Farming, Nature, Puzzle, Gardening
- `−25` Player Elimination, `−20` Take That, `−15` Real-Time
- `−20` wargames rank, `−10` categories Horror / Fighting / Wargame

### Social
- `+30` Social Deduction or Hidden Roles, `+25` Negotiation, `+20` Trading
- `+20` each (cap 40): Voting, Acting, Storytelling, Team-Based Game, Communication Limits
- `+20` partygames rank, `+10` familygames rank
- `+10` if `maxplayers >= 6`
- `−20` if `maxplayers == 2`, `−15` abstracts rank
- Language dependence "no necessary text" → `+5`

### Playful
- Base: `70 − (weight − 1) / 4 × 55`
- `+20` categories Party Game / Humor / Children's Game
- `+15` each (cap 30): Dexterity, Flicking, Stacking and Balancing, Push Your Luck, Acting
- `+10` categories Word Game / Trivia
- `+10` if `maxplaytime <= 30`, `+5` if `minage <= 8`
- `−20` wargames rank, `−15` if `maxplaytime >= 120`

### Compete
- **Hard rule:** Cooperative Game mechanic → score `≤ 10`, skip everything else. A co-op is not competitive, no matter what else it has.
- `+30` Player Elimination, `+25` Take That
- `+15` each (cap 45): Area Majority / Influence, Auction/Bidding, Betting and Bluffing, King of the Hill, Territory Building, Direct conflict-y attack mechanics
- `+20` wargames rank, `+10` strategygames rank
- `−15` Solo / Solitaire Game

### Intense
- Base: `(weight − 1) / 4 × 35`
- `+25` Real-Time, `+20` Traitor Game, `+20` Player Elimination
- `+15` thematic rank, `+15` wargames rank
- `+10` categories Horror / Fighting / Adventure
- `+15` if `maxplaytime >= 120`, `+10` if `maxplaytime >= 180`
- `−20` childrensgames rank, `−15` categories Party Game / Children's Game

## 3. Normalisation

Clamp raw to 0–100, then also store a **percentile** within the collection.

Display the percentile on the radar (so his 133 games actually spread across the chart instead of clustering mid-range), but keep the raw score as the stored value — percentiles shift every time a game is added, raw scores don't. Recompute percentiles at build time.

---

## 4. File layout

Two files, never merged:

**`vibes-auto.json`** — regenerated by the scorer, safe to blow away.
```json
{ "13": { "cozy": 41, "social": 22, "playful": 18, "compete": 78, "intense": 64, "thinky": 71 } }
```

**`vibes-manual.json`** — hand corrections, never written by the scorer.
```json
{ "13": { "compete": 90, "note": "way meaner at 5p than the tags suggest" } }
```

Merge at build time, manual wins per-axis (partial overrides allowed — correcting Compete shouldn't force him to restate the other five). Record `source: "manual" | "auto"` per axis in the merged output so the UI can mark hand-verified games.

Keys are BGG ids. The ~26 shelf games not yet on BGG have no ids and no auto data — give them local `local:` keys and manual-only scores.

---

## 5. Validation

This is the part that decides whether the whole thing is trustworthy.

1. Hand-score the games he's actually played, in `vibes-manual.json`, **before** looking at the auto output.
2. Compute mean absolute error per axis between auto and manual.
3. Report a per-axis table.

Target MAE < 15. Read it per-axis, not overall:

- Axis passing on played games → trust the auto scores on unplayed games.
- Axis consistently off in one direction → adjust that axis's base constant only.
- Axis with high scatter and no bias → the BGG tags don't carry that axis. Cozy and Intense are the likely failures. Mark that axis low-confidence in the UI rather than fudging weights until it fits.

Do not tune weights against the manual set until the MAE is near zero — that's overfitting to 60 games, and the whole point is generalising to the other 73.

---

## 6. Match score

Given a request (any subset of the six axes, plus player count and time):

1. **Hard filters first** — player count must be in range (prefer the `suggested_numplayers` best/recommended result over raw min/max), and `maxplaytime` within budget.
2. **Distance** on requested axes only: `100 − sqrt(mean((requested − actual)²))`.
3. Axes the user didn't set are ignored entirely — no implicit target.
4. Show the top match plus its radar and the best-player-count bar, per the layout he's been looking at.

---

## 7. Build output

Same delivery as today: bake the merged vibe data into the single self-contained `index.html`, no runtime BGG calls. Scorer runs on the laptop where the MCP server lives; the page stays static.
